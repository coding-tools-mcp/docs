The correct configuration depends first on where the client runs, not on the client's brand:

| Client environment | Recommended connection | Authentication |
| --- | --- | --- |
| A desktop or CLI client on the same computer as the repository | stdio, launched by the client | Not needed beyond the local process boundary |
| A URL-based tool on the same computer | loopback Streamable HTTP at `http://127.0.0.1:8765/mcp` | Local-only use; do not expose it publicly |
| ChatGPT, Grok, claude.ai, mobile, or another cloud client | authenticated HTTPS tunnel or the [Desktop app](/desktop) | Bearer, Token in URL, Basic, or OAuth depending on the client |
| A teammate's machine or a shared server | deliberately operated HTTPS deployment | Scoped credential owned by the operator |

If you are unsure, read [Choose your setup](/getting-started/choose-your-setup) first. Do not paste a public endpoint into a client until you know which secret authorizes it.

## Protocol compatibility

Two protocol eras are served at once. A client that speaks `2026-07-28` needs no configuration and no handshake: it discovers the server with `server/discover` and states its version in every request. A handshake client uses `2025-11-25`, and `2025-06-18` remains supported for existing clients.

You normally do not need to configure a protocol version manually. If a client behaves as though it negotiated an older protocol, read the `protocolVersion` returned in `InitializeResult` rather than assuming the requested version was accepted.

## The standard local stdio entry

Most local clients use the same JSON shape. Replace `/path/to/repo` with the real workspace folder:

```json
{
  "mcpServers": {
    "coding-tools": {
      "command": "uvx",
      "args": ["coding-tools-mcp", "--stdio", "--workspace", "/path/to/repo"]
    }
  }
}
```

Node.js equivalent:

```json
{
  "mcpServers": {
    "coding-tools": {
      "command": "npx",
      "args": ["--yes", "coding-tools-mcp", "--stdio", "--workspace", "/path/to/repo"]
    }
  }
}
```

After editing a client configuration, restart or reload that client. GUI-launched clients often do not inherit your terminal `PATH`; if `uvx` works in a terminal but the client cannot launch it, use the absolute path reported by `which uvx` or `which npx`.

## Codex

Add this to the Codex MCP configuration:

```toml
[mcp_servers.coding_tools]
command = "uvx"
args = ["coding-tools-mcp", "--stdio", "--workspace", "/path/to/repo"]
```

Use an absolute workspace path. If you use `npx`, put `--yes` in the argument list before `coding-tools-mcp`.

```json
{
  "servers": {
    "coding-tools": {
      "type": "stdio",
```

For a local HTTP server, use `"type": "http"` with `"url"` and, when needed, `"headers"` keys. Keep the HTTP server on loopback unless you have deliberately added authentication and outer isolation.

## Gemini CLI

One command, project scope by default:

```bash
gemini mcp add coding-tools -- uvx coding-tools-mcp --stdio --workspace /path/to/repo
```

Or edit `~/.gemini/settings.json` (user scope) or `.gemini/settings.json` (project scope):

```json
{
  "mcpServers": {
    "coding-tools": {
      "command": "uvx",
      "args": ["coding-tools-mcp", "--stdio", "--workspace", "/path/to/repo"]
    }
  }
}
```

For the local HTTP server, transport `http` replaces the command entirely:

```bash
gemini mcp add --transport http coding-tools http://127.0.0.1:8765/mcp
```

Authenticated endpoints take `--header "Authorization: Bearer <token>"`. Keep the server name free of underscores: Gemini CLI derives tool names from it and splits on the first one.

## Generic local HTTP clients

Start the server on loopback:

```bash
uvx coding-tools-mcp --workspace /path/to/repo --port 8765
```

Configure the client with:

```text
http://127.0.0.1:8765/mcp
```

This endpoint is designed for local loopback use. Do not bind it to a public interface without external authentication and sandboxing.

## Remote MCP and cloud clients

For remote MCP clients, keep the server on loopback and expose it through an HTTPS tunnel with authentication. The fixed tool set includes mutation and command execution, so a public endpoint must never be unauthenticated.

Before using `--auto-install-tunnel` on macOS, install `cloudflared` manually unless Homebrew is already available; the script's direct-download fallback does not handle Cloudflare's macOS `.tgz` package.

Install [`uv`](https://docs.astral.sh/uv/getting-started/installation/) first when possible. Without `uv`, the installer falls back to `pip install --user`; externally managed Python installations can reject that fallback before the tunnel starts.

```bash
curl -fsSL https://raw.githubusercontent.com/xyTom/coding-tools-mcp/main/scripts/install.sh \
  | bash -s -- --tunnel cloudflared --auto-install-tunnel --auth-mode bearer --workspace /path/to/repo
```

Configure the remote client with:

```text
URL: https://<tunnel-host>/mcp
```

Static bearer-token auth is available for clients that support custom `Authorization` headers. OAuth-aware MCP clients can use the OAuth tunnel, which publishes protected-resource and authorization-server discovery plus RFC 7591 dynamic registration and a PKCE authorization flow. Clients that support neither require an external authenticated proxy or a Desktop-provided compatibility auth method. See [Remote access](/guides/remote-access).

## ChatGPT

ChatGPT is a cloud client: it cannot launch `uvx` or reach `127.0.0.1` on your computer. You need a public HTTPS endpoint.

### Recommended for most people: Desktop app

The simplest path is the [Desktop app](/desktop):

1. Create a workspace with **Temporary sharing** or **Stable public access**.
2. Choose **Token in URL** authentication.
3. Start the workspace and click **Copy endpoint**. The copied URL already contains the secret token.
4. In ChatGPT, add a custom MCP server/plugin, paste the URL, and select **No authentication** because the token is already in the URL.
5. Verify with a real read-only project request.

Exact ChatGPT labels vary by plan, workspace, and rollout. Treat the complete `?token=` URL as a password. Do not paste it into screenshots, issues, logs, or chat messages.

### Advanced direct-core path: OAuth tunnel

If you operate the core directly, start an OAuth tunnel:

```bash
curl -fsSL https://raw.githubusercontent.com/xyTom/coding-tools-mcp/main/scripts/install.sh \
  | bash -s -- --tunnel cloudflared --auto-install-tunnel --auth-mode oauth --workspace /path/to/repo
```

In ChatGPT, create a custom connector or MCP app pointing at `https://<tunnel-host>/mcp`. If ChatGPT discovers the OAuth endpoints itself, the authorization page asks for the password printed by the script. If the connector form asks for details instead, fill them in:

- Authorization URL: `https://<tunnel-host>/oauth/authorize`
- Token URL: `https://<tunnel-host>/oauth/token`
- Client ID and secret: from a pre-registered client — start the tunnel with `CODING_TOOLS_MCP_OAUTH_CLIENT_ID`, `CODING_TOOLS_MCP_OAUTH_CLIENT_SECRET`, and `CODING_TOOLS_MCP_OAUTH_REDIRECT_URIS` set to the redirect URI ChatGPT shows.

## Grok

grok.com is also cloud-only. Start the same OAuth tunnel, then add a custom connector at grok.com/connectors (Settings → Connectors) with `https://<tunnel-host>/mcp`; Grok completes the OAuth flow in a popup.

The xAI API takes the static bearer tunnel instead — a request's remote MCP tool entry pins the server and the header:

```json
{
  "server_url": "https://<tunnel-host>/mcp",
  "server_label": "coding_tools",
  "authorization": "<CODING_TOOLS_MCP_AUTH_TOKEN>"
}
```

Only Streamable HTTP and SSE transports are supported on Grok's side, which is what the tunnel already speaks.

## Verify the client before trusting it

After configuration, use this acceptance sequence:

1. Ask the client to list or inspect the repository without making changes.
2. Confirm that the answer names files that really exist in the intended workspace.
3. Ask for one small reviewable change.
4. Inspect `git status --short` and `git diff` yourself.
5. For a public endpoint, verify that an unauthenticated request cannot use the MCP endpoint.

Good first prompt:

```text
Inspect this repository and summarize its structure. Do not modify files or run commands yet.
```

If this fails, go to [Troubleshooting](/troubleshooting) and identify the failing layer first: client configuration, process launch, loopback server, tunnel reachability, authentication, or workspace permission.
